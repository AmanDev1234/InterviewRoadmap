🍃 MongoDB — Complete Interview Preparation

BASIC Fundamental Concepts You Must Know Cold

1. Document Model & BSON

MongoDB stores data as BSON documents (Binary JSON). Unlike relational tables, documents in a collection can have different structures. BSON extends JSON with types like Date, ObjectId, Binary, and 32/64-bit integers.

🎯 CEO Explanation
Think of MongoDB like a filing cabinet where each folder can hold different types of documents — some have receipts, some have photos, some have contracts. SQL would be like a spreadsheet where every row must have exactly the same columns. MongoDB gives you flexibility when your data isn't uniform.
Q: What is the difference between MongoDB and SQL databases?

Model Answer: MongoDB is a document-oriented NoSQL database that stores data as flexible JSON-like documents, while SQL databases use rigid table schemas with rows and columns. The key trade-offs are: MongoDB offers schema flexibility and horizontal scalability out of the box, making it ideal for rapidly evolving data models and high-write workloads. SQL databases provide stronger consistency guarantees through ACID transactions and are better for complex relational queries with JOINs. In practice, I choose MongoDB when the data model is evolving or when I need to scale writes horizontally, and SQL when data relationships are complex and well-defined.

🔄 Cross-Question
Interviewer: "When would you NOT use MongoDB?" — Be ready with specific examples: highly relational data (banking), complex multi-entity transactions, or when your team has deep SQL expertise and the use case doesn't benefit from document flexibility.
🚩 Red Flag
Saying "MongoDB is better than SQL" without context. Always frame it as trade-offs based on use case. Interviewers want to see engineering judgment, not technology tribalism.
Q: What is ObjectId and how is it constructed?

Model Answer: ObjectId is a 12-byte identifier that MongoDB auto-generates for the _id field. Its structure is: 4 bytes timestamp (seconds since epoch) + 5 bytes random value (machine/process identifier) + 3 bytes incrementing counter. This design means ObjectIds are roughly sortable by creation time, globally unique without coordination, and don't require a central authority. I can extract the creation timestamp from any ObjectId using objectId.getTimestamp().

🔄 Cross-Question
Interviewer: "What if I want to use a custom _id?" — Explain that you can set your own _id (like a UUID or composite key), but you lose auto-generation and the embedded timestamp benefit. Also, custom _ids must be unique within the collection.

2. CRUD Operations & Query Operators

Beyond basic find/insert, you must understand query operators: comparison ($gt, $lt, $gte, $lte, $ne, $in), logical ($and, $or, $not, $nor), element ($exists, $type), array ($elemMatch, $size, $all), and evaluation ($regex, $expr). Update operators like $set, $unset, $push, $pull, $addToSet are equally important.

Q: Explain $elemMatch with a real example.

Model Answer: $elemMatch matches documents where an array field contains at least one element matching ALL the specified criteria. For example, if I have a products collection with a "variants" array containing {color, size, price}, and I want products that have a variant that is BOTH red AND under $50, I use: {variants: {$elemMatch: {color: "red", price: {$lt: 50}}}}. Without $elemMatch, a regular query {"variants.color": "red", "variants.price": {$lt: 50}} would match if ONE variant is red and a DIFFERENT variant is under $50 — which is not what we want.

🔄 Cross-Question
Interviewer: "What's the performance impact of querying array fields?" — MongoDB creates multikey indexes for array fields (one index entry per array element). This means larger indexes and slower writes, but efficient reads. Also, you can only have one multikey index per compound index.

3. Indexing Fundamentals

Indexes are THE most important MongoDB performance topic. Without proper indexes, MongoDB performs collection scans. Key types: single field, compound, multikey (array), geospatial, text, and hashed. Use explain() to verify index usage.

🎯 CEO Explanation
An index is like the index at the back of a textbook. Without it, finding "all pages mentioning MongoDB" means reading every single page. With the index, you jump directly to the right pages. The trade-off: the index takes up space and slows down inserts.
Q: How do you decide the order of fields in a compound index?

Model Answer: The ESR rule: Equality first, Sort second, Range last. Fields used in equality matches come first, then fields used for sorting, then fields used for range queries. For example, if my query is {status: "active"}.sort({createdAt: -1}).where({price: {$lt: 100}}), my compound index should be {status: 1, createdAt: -1, price: 1}. I verify this using explain("executionStats") to check for COLLSCAN vs IXSCAN.

🚩 Red Flag
Not knowing the ESR rule at 4 YOE. Also, saying "add indexes to everything" — over-indexing kills write performance.
INTERMEDIATE Architecture Patterns, Best Practices & Performance

1. Schema Design Patterns

The fundamental decision: Embedding vs Referencing. Embedding puts related data in a single document. Referencing stores related data separately and links via ObjectId.

FactorEmbedReference
Data accessAlways read togetherOften accessed separately
Growth patternBounded, small arraysUnbounded growth
ConsistencyStrong (single doc)Eventual (multi-doc)
Write frequencyRarely updatedFrequently updated
16MB limitMust fit in one docCan exceed via references
Q: How would you design a schema for a blog system with posts and comments?

Model Answer: It depends on scale. For a typical blog with under 10,000 comments per post, I'd embed comments because they're always read with the post and the document stays under 16MB. For viral posts with unbounded comments, I'd reference — store comments in a separate collection with a postId. I'd also use the Bucket Pattern for paginated comments. Key: start with embedding for simplicity, add referencing only when scale demands it.

🔄 Cross-Question
Interviewer: "What if comments need to be searchable independently?" — Then referencing is better because you can index and query the comments collection directly.

2. Aggregation Framework

The aggregation pipeline processes documents through stages: $match, $group, $project, $sort, $limit, $lookup, $unwind, $facet. Always put $match early to reduce documents flowing through the pipeline.

Q: Design an aggregation to find the top 5 product categories by revenue this month.
db.orders.aggregate([ { $match: { createdAt: { $gte: ISODate("2024-01-01") } } }, { $unwind: "$items" }, { $group: { _id: "$items.category", totalRevenue: { $sum: { $multiply: ["$items.price", "$items.quantity"] } }, orderCount: { $sum: 1 } }}, { $sort: { totalRevenue: -1 } }, { $limit: 5 } ])

Key: $match first for performance, $unwind to flatten items, $group to aggregate, then sort and limit. Add an index on createdAt.

3. Transactions & Consistency

MongoDB supports multi-document ACID transactions (since 4.0). Prefer schema design that keeps atomic operations within a single document. Use transactions only when cross-document consistency is truly needed.

Q: When should you use MongoDB transactions vs embedding?

Model Answer: My first choice is always schema design where atomic operations fit in a single document — single-document ops are inherently atomic. I use multi-document transactions when: (1) Cross-document consistency is truly needed (bank transfers), (2) Data is too large or changes too frequently to embed, (3) Multiple collections need atomic updates. Most use cases can be handled with proper schema design without transactions. When I do use them, I keep transactions short-lived and retry on write conflicts.

🚩 Red Flag
Using transactions for every operation = treating MongoDB like SQL. Also, not knowing transactions require a replica set.
ADVANCED Scalability, Security & Production Operations

1. Sharding & Horizontal Scaling

Sharding distributes data across machines using a shard key. Range-based sharding supports range queries but creates hotspots. Hash-based sharding distributes evenly but loses range optimization. Zone sharding pins data to specific shards.

Q: How do you choose a shard key?

Model Answer: Three properties: (1) High cardinality — many distinct values for even distribution. (2) Low frequency — no single value dominates. (3) Non-monotonically changing — avoids hotspots on inserts. For example, hashed userId is good for even distribution, but if most queries filter by region, I'd use {region: 1, userId: 1} with zone sharding. The worst shard key creates a single "hot" shard receiving all writes.

2. Replica Sets & Read/Write Concerns

One primary (writes) + multiple secondaries. Read preferences: primary, primaryPreferred, secondary, secondaryPreferred, nearest. Write concerns: w:1, w:majority, w:0. Balance consistency vs performance based on your application's needs.

Q: What happens when the primary node fails?

Model Answer: Automatic election: secondaries detect primary is unreachable via heartbeat (2s interval, 10s timeout). The secondary with the most up-to-date oplog typically wins. During election (5-10s), no writes accepted but reads continue from secondaries. I ensure an odd number of voting members and use writeConcern: majority for critical data.

🚂 Express.js — Complete Interview Preparation

BASIC Request-Response Cycle & Middleware Fundamentals

1. The Middleware Stack

Every request passes through middleware functions receiving req, res, and next(). Middleware can execute code, modify req/res, end the response, or call next(). Order matters — they execute in the order added.

🎯 CEO Explanation
Express middleware is like a security checkpoint at an airport. Each station can let you through (next()), stop you (res.send()), or modify you (add data to req). If any station stops you, you never reach the gate (route handler).
Q: Explain the difference between app.use() and app.get()/app.post().

Model Answer: app.use() mounts middleware for ALL HTTP methods on matching paths. app.get()/app.post() are route handlers for specific methods. Key subtlety: app.use('/api', handler) matches /api, /api/users, /api/users/123 — it's prefix-based. app.get('/api', handler) matches ONLY /api exactly. I use app.use() for cross-cutting concerns (logging, auth, CORS) and app.METHOD() for specific route handlers.

🔄 Cross-Question
Interviewer: "What happens if you forget to call next() or send a response?" — The request hangs forever. This is one of the most common Express bugs.

2. Error-Handling Middleware

Error-handling middleware has four parameters: (err, req, res, next). Express recognizes it by the four parameters. When you call next(err) with an argument, Express skips regular middleware and jumps to the first error handler.

Q: How do you handle async errors in Express routes?

Model Answer: Express doesn't catch async errors automatically. I use a wrapper function:

const asyncHandler = (fn) => (req, res, next) => { Promise.resolve(fn(req, res, next)).catch(next); }; // Usage: app.get('/users/:id', asyncHandler(async (req, res) => { const user = await User.findById(req.params.id); if (!user) throw new AppError(404, 'User not found'); res.json(user); }));

This keeps route handlers clean — no try/catch boilerplate. All errors flow to the global error handler. I create AppError with status codes for consistent error responses.

🚩 Red Flag
Not having a global error handler at 4 YOE. Also, unhandled promise rejections — in Node 15+ these crash the server.
INTERMEDIATE Security, Validation & Performance

1. Security Middleware Stack

Essential: helmet (security headers), cors (cross-origin), express-rate-limit (DDoS protection), and input validation (Joi/Zod). Always sanitize inputs to prevent NoSQL injection.

Q: How do you prevent NoSQL injection in Express?

Model Answer: Three layers: (1) Input validation with Joi/Zod that strictly defines expected types and rejects objects. (2) Sanitization middleware that strips $ and . characters from req.body/params/query — I use express-mongo-sanitize. (3) Mongoose with strict schemas — Mongoose casts values to schema types, neutralizing many injection attempts. I never pass user input directly to MongoDB queries without validation.

2. Pagination Patterns

Cursor-based vs offset-based. Cursor-based: client sends last document's ID, server queries {_id: {$gt: cursor}}.limit(n). More efficient for large datasets. Offset-based: .skip(page * limit).limit(limit) — simpler but slow for deep pages.

Q: Compare cursor-based and offset-based pagination.

Model Answer: Cursor-based is superior for large datasets: MongoDB doesn't skip documents, it uses the index to jump directly. It's consistent even if data changes between pages (no duplicate/missing items). However, you can't jump to page 50 directly. Offset-based is simpler and supports random page access, but .skip(n) scans n documents first, making deep pages very slow. For a product listing with millions of items, cursor-based was 5x faster for deep pages. I return metadata: totalCount, hasNextPage, nextPageCursor.

ADVANCED Microservices & Production Architecture

1. When to Break a Monolith into Microservices

Don't start with microservices. Extract when: (1) A module needs independent scaling. (2) Different uptime requirements. (3) Teams need independent deployment. (4) Distinct data consistency models. Before extracting, ensure clear API boundaries exist in the monolith.

Q: When would you break a monolithic Express app into microservices?

Model Answer: I start with a well-structured monolith and extract when there's clear need. Triggers: independent scaling requirements (report generation is CPU-heavy), different uptime SLAs (payments need 99.99%), team deployment independence, or distinct consistency models. I've seen premature decomposition create distributed system complexity without any benefit. Before extracting, I ensure the module has well-defined interfaces in the monolith — if the boundaries aren't clean in-process, they'll be worse over the network.

⚛️ React.js — Complete Interview Preparation

BASIC Core React Concepts & Component Fundamentals

1. Virtual DOM & Reconciliation

React maintains a virtual DOM in memory. When state changes, it creates a new virtual tree, diffs it against the previous one (reconciliation), and calculates the minimum DOM operations needed. The diffing assumes: different element types produce different trees, and keys mark stable child elements.

🎯 CEO Explanation
Imagine editing a document. Without virtual DOM, every keystroke reprints the entire page. With it, React compares what changed and only reprints that specific part. Like a smart assistant who updates only what's different.
Q: Why shouldn't you use index as a key in lists?

Model Answer: Using index as a key defeats reconciliation. When items are added, removed, or reordered, the index changes but the item at that position may differ. React sees the same key and assumes it's the same component, reusing the DOM node with wrong data. This causes visual bugs (inputs showing wrong values), performance degradation, and component state bugs. Always use a unique, stable identifier like a database ID.

🔄 Cross-Question
Interviewer: "Does the app break with wrong keys?" — No crash, but subtle bugs: wrong input values, animations targeting wrong elements. It's a silent killer in production.

2. useEffect & Component Lifecycle

useEffect combines componentDidMount, componentDidUpdate, and componentWillUnmount. Dependency array: no array = every render, [] = mount only, [deps] = when deps change. Cleanup function runs before next effect and on unmount.

Q: What are common useEffect mistakes?

Model Answer: (1) Missing dependencies — causes stale closures. I use eslint-plugin-react-hooks exhaustive-deps rule. (2) Not cleaning up — WebSocket connections and intervals without cleanup cause memory leaks. (3) Infinite loops — setting state inside useEffect without proper deps. (4) Object/array dependencies — new references every render trigger effects unnecessarily. Memoize with useMemo or move outside. (5) Fetching without AbortController — causes "can't perform state update on unmounted component" warnings.

🚩 Red Flag
Not understanding useEffect cleanup and stale closures at 4 YOE. Interviewers probe this deeply.

3. Controlled vs Uncontrolled Components

BASIC Event Loop, Async Model & Core Modules

1. The Node.js Event Loop

Phases: timers → pending callbacks → idle/prepare → poll (I/O) → check (setImmediate) → close callbacks. Between phases, microtask queue runs: process.nextTick first, then Promises.

🎯 CEO Explanation
Like a restaurant waiter (single thread) handling many tables. When table 1 orders, the waiter gives the order to the kitchen (async I/O) and moves to table 2. When food is ready (callback), the waiter delivers it. The waiter never cooks — just coordinates.
Q: What's the output: console.log('1'); setTimeout(() => console.log('2'), 0); Promise.resolve().then(() => console.log('3')); process.nextTick(() => console.log('4')); console.log('5');

Output: 1, 5, 4, 3, 2

1 and 5 are synchronous. Then microtask queue: nextTick (highest priority) then Promises. setTimeout(0) goes to timers phase after microtasks. setTimeout(fn, 0) doesn't mean "immediately" — it means "next timers phase."

🔄 Cross-Question
Interviewer: "Difference between process.nextTick and Promise.then?" — nextTick runs before Promise microtasks and can starve the event loop if used recursively. Prefer Promises; nextTick is for library-level needs.

2. Streams & Buffers

Four types: Readable, Writable, Duplex, Transform. Streams process data piece-by-piece without loading everything into memory. Use for files >100MB, video processing, real-time data.

Q: How would you process a 5GB file in Node.js?

Model Answer: Never load it with fs.readFile. Use fs.createReadStream with pipe or async iteration: for await (const chunk of createReadStream('large.csv')) { processLine(chunk); }. With highWaterMark of 64KB, only 64KB is in memory at any time. For CSV, I use Transform streams: read → transform → write. Peak memory under 100MB regardless of file size. Handle backpressure automatically.

Cluster forks multiple processes, each with its own event loop, sharing the same port. Worker Threads share memory via SharedArrayBuffer within a single process. Use Cluster for scaling HTTP connections, Worker Threads for CPU-intensive tasks within a request.

Q: When would you use Worker Threads vs Cluster?

Key insight: Cluster scales the server, Worker Threads offload CPU work within a request.

2. Memory Leaks & Profiling

Common causes: global variables, closures holding references, uncleared event listeners/timers, unbounded caches. Detect with process.memoryUsage(), --inspect + Chrome DevTools, heap snapshots. Set alerts at 80% of --max-old-space-size.

Q: How do you diagnose a memory leak in production?

Model Answer: Confirm with process.memoryUsage() — if heapUsed grows consistently and never drops after GC, it's a leak. Take heap snapshots at intervals using --inspect: normal load vs post-leak. Compare in Chrome DevTools "Comparison" view. Look for: retained size (what holds memory GC can't collect), GC roots (what keeps objects alive). Common culprits: closures capturing large objects, Maps without eviction, event emitters with stale listeners. Found one case: WebSocket connection map that never removed entries on disconnect — fixed with cleanup on 'disconnect' event.

Q: StatelessWidget vs StatefulWidget?

Rule: always understand what constraints a widget receives before debugging its size.

Model Response
React maintains a tree of JavaScript objects representing the UI — the virtual DOM. When state or props change, React creates a new virtual tree for the affected component subtree. It then runs the diffing algorithm (reconciliation) comparing the new tree with the previous one. The key rules: if element types differ, it tears down the old tree and builds new; if types match, it updates props and recurses into children; for lists, it uses keys to match old and new children. Important: the render phase (diffing) is interruptible in React 18 with concurrent features, but the commit phase (DOM updates) is always synchronous. That's why we can have features like useTransition — the diffing can be paused for urgent updates, but once committed, the UI is consistent.

Sample Project Description — Template 2: Mobile Field Sales App

Results: Reps could create orders in zero-connectivity areas. Sync reliability was 99.7% — the 0.3% were genuine conflicts that required manual resolution (which we flagged in the UI). Order creation time dropped from 8 minutes (paper-based) to 2 minutes (app). This was my first offline-first architecture, and it taught me to design for failure from the start.

E

D
Differentiate
